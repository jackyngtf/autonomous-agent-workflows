# 透過書面程序累積事件經驗

[English](self-improvement-loop.md) · [**繁體中文**](self-improvement-loop.zh-TW.md)

這裡所說的「self-improvement」，是以檔案維護操作知識：記錄事件、查閱相關歷史，並在有依據時修改程序。這不是模型訓練。現有紀錄未量度失敗率是否下降，也不保證同一錯誤不會再出現。

## 由觀察形成程序

1. 記錄問題、日期、流程及執行環境。
2. 搜尋相關歷史發現，檢查目前證據。
3. 區分實際回應與推測成因。
4. 記錄嘗試的操作、結果及未解決問題。
5. 有充分依據時，在授權範圍內修訂程序，並檢查修改後的行為。

例如 CSV 內出現類似掃描探測的內容，是一項觀察。識別遠端來源或確認完整成因，仍需要其他證據。程序修訂應連回來源事件，說明修改的規則。記錄經驗不構成擴大寫入、刪除或其他政策邊界的授權。

## 按需要檢索

預期方式是完整閱讀現行程序，再於錯誤或不確定情況令歷史資料變得相關時搜尋：

```sh
rg -n -i 'smb|STATUS_INVALID_PARAMETER' .learnings/
rg -n -i 'header|row count|validation' .learnings/
```

應閱讀足夠前後文，理解搜尋結果。某個 NAS 版本或 API 請求的發現，不是通用規則。公開範本不包含私人 `.learnings/` 歷史檔案。

## 只附加歷史與整理

歷史程序同時包含執行後附加條目，以及每月合併、刪減及輪替。如果整理刪除或改寫條目的唯一副本，歷史就不再是完整的只附加紀錄。

較清楚的未來保留模式，是在保留或有版本紀錄的歷史中保存原始事件、標示已被取代的結論，並在 work instruction 獨立維護現行規則。搜尋摘要可以濃縮，同時保留原始條目的連結。未解決問題應維持明確的未解決狀態。

這是建議，不代表現有歷史保留了每次修訂。整理報告是某次執行的記載，不是對所有保留或移除內容的獨立審計。

## 月底處理與補做

紀錄中的設計是在每月最後工作日整理文件，計算時包括維多利亞州公眾假期，並在漏做後補做。實作需要記錄應處理月份、嘗試結果及最後成功完成月份。失敗的嘗試不應推進完成標記。

日期應使用 `Australia/Melbourne` 計算；固定 UTC+10 不能代表墨爾本全年時間。文件維護應與工作簿發佈分開，避免文件處理失敗觸發重複匯出。

[NAS 報告範例](../examples/nas-access-log/sample-report.zh-TW.md)現已明確標示為合成內容，不再聲稱 2026 年 7 月 29 日是該月最後工作日，也不是整理曾經執行的證據。

## 改善的證據

事件案例可以展示失敗、程序或程式修改、能偵測該失敗的檢查，以及附有執行模式和限制的後續結果。若要比較失敗率，還需要完整執行嘗試紀錄及可比較的觀察時段。

作品集能支持的說法，是事件經驗促成了指引及驗證修改。[離線示範](../demo/README.zh-TW.md)令部分檢查可以重現，但不能追溯驗證正式執行歷史。
