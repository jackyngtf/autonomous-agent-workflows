# 06 · 心得與限制

[English](06-lessons-and-limitations.md) · [繁體中文](06-lessons-and-limitations.zh-TW.md) · [專案概覽](../../README.zh-TW.md)

最有價值的成果，是更清楚的操作程序：哪些證據容許更新、哪些內容需要獨立檢查，以及遇到甚麼情況必須停止。

## 我會保留的設計決定

- **用確定性程式實作穩定規則。** 日期計算、欄位檢查、分組及值比較，應清楚且可測試。Agent 判斷較適合用於例外及診斷。
- **規劃恢復前先檢查目的地。** 本機歷史可能不完整，而其他工作階段早已發布結果。
- **讓缺失保持可見。** 保留異常檔案或列出無法取得的日期，比默默產生看似合理的活頁簿更有資訊價值。
- **區分事件歷史與現行指引。** 需要時才搜尋詳細歷史；操作程序則集中描述目前規則。
- **將發布與清理分開決定。** 本機重建成功，不代表已發布的版本正確。

## 現有證據的邊界

歷史報告由執行工作階段撰寫，並非獨立稽核證明。驗證方式曾演進，部分檢查採用抽樣。有些報告與後續觀察互相矛盾；[證據說明](../evidence/README.zh-TW.md)保留了這些不確定性。

知識整理可能重寫或刪減工作筆記。將這些檔案稱為永久只增不改，會誇大其稽核能力。持久的稽核軌跡需要保留原始版本，或使用不可變的事件歷史。

9 月恢復輔助程式包含該次工作階段專用的日期與假設。它們能說明當時如何恢復，但不是可直接部署的通用流程函式庫。公開示範則是使用合成資料的獨立本機實作。

## 下一步會改善甚麼

| 改善項目 | 原因 |
|---|---|
| 穩定執行識別碼及集中歷史 | 核對排程、手動、中止及由外部完成的工作。 |
| 具名時區與夏令時間測試 | 以真正的墨爾本時區規則取代歷史程式中的固定 UTC+10。 |
| 嚴格處理 API 完整性 | 批次達上限時，縮小查詢範圍或停止，不能只發出警告。 |
| 明確的活頁簿比較約定 | 定義哪些值及中繼資料必須在重建後保留。 |
| 操作指引與事件紀錄版本管理 | 保留變更原因，並避免把可修改筆記當成不可變證據。 |
| 明確恢復責任與來源保留政策 | 依已確認的系統設定，訂立升級處理及恢復預期。 |

這些是工程改善重點，不表示歷史部署已經全部具備。即使離線程式已展示某項改進，部署前仍須在實際整合環境驗證。
