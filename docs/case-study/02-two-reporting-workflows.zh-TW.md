# 02 · 兩項報表流程

[English](02-two-reporting-workflows.md) · [繁體中文](02-two-reporting-workflows.zh-TW.md) · [專案概覽](../../README.zh-TW.md)

兩項流程都產生每月活頁簿，但輸入與恢復政策不同。

| 判斷項目 | PBX 通話報表 | NAS 存取報表 |
|---|---|---|
| 輸入 | 獨立接收器產生的每日 SMDR CSV | NAS API 提供的檔案傳輸事件 |
| 預定排程 | 墨爾本時間平日上午約 10 時 | 墨爾本時間平日上午約 9 時 |
| 可處理日期 | 截至昨日的完整日期 | 截至昨日的完整日期 |
| 工作表分組 | 每份符合條件的每日 CSV 一張工作表 | 工作日各一張；同月份的連續非工作日合併 |
| 既有涵蓋範圍 | 新增日期前先檢查工作表 | 規劃前檢查月報並確認涵蓋範圍 |
| 無效或無法取得的輸入 | 保留異常檔案並報告 | 調查零筆資料的日期，明確列出無法取得的歷史資料 |
| 發布後處理 | 驗證輸出後才清理符合條件的來源檔 | 不刪除來源紀錄 |

排程描述的是預期運作方式，不能用來證明每個排程工作階段都有啟動或完成。

## 共用的處理路徑

1. 檢查執行環境與必要相依套件。
2. 檢查來源輸入及實際目的地活頁簿。
3. 規劃尚未涵蓋、而且已完整結束的日期。
4. 以既有表格紀錄及新增工作表重建月報。
5. 驗證本機輸出、發布檔案，再下載已發布的版本進行檢查。
6. 記錄新增內容、略過項目、失敗及需要人工處理的事項。

每個月份各自使用一份活頁簿。補回資料的工作階段可以更新兩個月份，但合併的工作表不可跨月。

## 不同輸入帶來不同風險

通話紀錄中的異常 CSV 可以保留以供調查。6 月 15 日的報告記錄了新增一份有效檔案，同時保留含二進位資料的檔案。來源清理是驗證後的獨立決定；解析成功本身不足以支持刪除。

NAS 的原始事件則可能不再能從即時 API 取得。9 月 15 日恢復時，部分舊日期已無法查回。建立空白工作表會掩蓋缺口，因此報告保留了缺失的說明，並繼續處理仍可取得的日期。

## 為何先檢查目的地？

本機報告可能缺漏，但其他工作階段已更新目的地。兩項 9 月恢復案例都遇到這個情況。直接沿用舊的補回計畫，可能重複處理或錯報積壓量。Agent 必須以實際讀取的活頁簿重新核對計畫。
