# NAS 存取紀錄流程：程序參考

[English](WORKINSTRUCTION.md) · [**繁體中文**](WORKINSTRUCTION.zh-TW.md)

> 重新編寫的設計參考，不是可執行的部署指南。不包含憑證或真實驗證程式。本專案觀察到的 NAS 行為，需要在新環境重新確認。

## 用途與來源邊界

歷史流程收集 Synology 檔案傳輸活動，將缺漏日期加入月報。原排程為平日 09:00。程序使用 SyslogClient、`logtype=cifs`、每小時查詢視窗及 50,000 筆回傳上限。

這些是有紀錄的整合選擇，不是所有 DSM 版本都支援的 API 約定。驗證要求、分頁、篩選及保留期間，必須在目標系統確認。達上限的回應可能遭截斷；HTTP 請求成功本身不能證明結果完整。

公開 [JSON 測試資料](../../sample-data/nas-syslog/nas_access_records_2026-08-04.json)為合成內容。[本機解析器](../../demo/workflows.py)檢查指定欄位及時間戳記，不會呼叫 NAS。

## 日期與報表政策

使用 `Australia/Melbourne` 轉換時間戳記及判斷目前日期，排除當日與未來紀錄。歷史設計使用維多利亞州工作日，並在同一月份內合併連續非工作日。

離線示範刻意改用每個已完成本地日期一張工作表，包含週末，並分開月份。它沒有實作歷史假期分組政策。正式連接模組需要明確定義所選政策，包括零筆資料日期及來源保留缺口。

## 程序與失敗邊界

| 步驟 | 操作 | 必要決策或檢查 |
|---|---|---|
| 1. 檢查 | 確認目的地實際涵蓋日期及來源可用性 | 過時報告不是權威；無法讀取不等於不存在 |
| 2. 取得 | 透過設定的連接模組查詢所需時段 | 偵測截斷、篩選錯誤、時間戳記缺口及失敗請求 |
| 3. 規劃 | 按明確日期政策分組已接受紀錄 | 區分已確認零筆資料與完整性未明 |
| 4. 準備 | 記錄既有資料快照並建立待驗證檔案 | 拒絕衝突更新，不無聲地替換既有紀錄 |
| 5. 驗證 | 比較預期工作表、列數及儲存格值 | 預期紀錄須獨立於重建結果準備 |
| 6. 發佈 | 透過正式目的地連接模組寫入 | 定義並行、備份及部分寫入恢復方式 |
| 7. 取回 | 下載並檢查已發佈副本 | 上傳後失敗屬於事件，不代表目的地未被修改 |
| 8. 報告 | 記錄涵蓋範圍、變更、驗證及未解決缺口 | 正確標示排程、手動及來源未明的執行模式 |

重建會替換檔案，目標是保留支援範圍內的表格紀錄，並非任意 Excel 功能。此流程不需要刪除來源日誌。

## 部署責任

負責人需要提供憑證方式、經實際 API 確認的必要最低權限、查詢視窗與分頁處理、保留政策及恢復方法。本專案觀察到的驗證處理方式，不應未經測試就推廣使用。公開參考刻意省略 HTTP 登入程式及權限假設。

文件維護與匯出分開。只有成功完成後才標記每月維護完成；如果需要完整審計軌跡，應保留原始事件歷史。詳見[知識維護](../../docs/self-improvement-loop.zh-TW.md)。
