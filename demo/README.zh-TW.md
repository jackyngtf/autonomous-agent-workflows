# 執行報表示範

[English](README.md) · **繁體中文** · [作品集](../README.zh-TW.md)

這是為作品集重新編寫的參考程式，以合成資料展示範圍明確、可檢查的報表流程。它不會重播歷史 Agent 執行、不會呼叫 LLM、連接 NAS 或刪除輸入。

## 先執行正常更新

在 repo 根目錄使用 Python 3.11 或以上版本：

```bash
python -m pip install -r requirements.txt
python -m demo --workflow all --output-dir output/demo
```

目的地首次建立時，示範會產生一個 2026 年 8 月 3 日工作表，內含一筆虛構既有紀錄，再加入 8 月 4 日的範例：Avaya 有 13 筆、每筆 30 欄；NAS 有八筆。兩份完成的工作簿各有兩個日期工作表，分別合共 14 及九筆資料。

```text
output/demo/
  avaya/
    2026-08.xlsx
    run-report.md
    evidence.json
  nas/
    2026-08.xlsx
    run-report.md
    evidence.json
```

開啟工作簿即可查看保留的前一日紀錄及新紀錄。雙語報告列出結果，JSON 則提供可核對的細節。輸入位於 [sample-data](../sample-data)，處理邏輯位於 [workflows.py](workflows.py)。

再次執行相同指令：若既有紀錄完全相符，結果為 `NO_CHANGE`，工作簿位元組不變。若同日期的工作表與輸入不一致，流程會停止，不會單憑日期存在就當作已完成。

## 查看驗證如何阻止更新

使用另一個輸出目錄，確保仍有待處理更新：

```bash
python -m demo --workflow all --scenario blocked --output-dir output/blocked
```

**預期結束代碼：2。** 這個情境會在寫入待發布檔案後修改其中一格。獨立讀取程式會逐格比較支援的內容與預期紀錄，發現差異並阻止發布。先前建立的工作簿及所有輸入範例均保留，清理資格維持為 false。

被修改的工作簿可以與正確版本具有相同列數及欄數；這正是要示範的問題：只核對尺寸不能證明內容一致。自動測試亦涵蓋重複標題列及不完整傳輸。

## 檢查範圍

| 邊界 | 本機參考版本的行為 |
|---|---|
| 輸入 | 精確結構、每列欄數、可解析日期、完整日期截止點及預期月份 |
| 既有工作簿 | 確認不存在才建立初始資料；無法讀取或包含不支援內容則報錯 |
| 待發布檔案 | 使用 openpyxl 比較全部支援的文字儲存格、工作表名稱及紀錄次序 |
| 模擬傳輸 | 複製到本機暫存檔、比較雜湊值，再重新讀取暫存副本 |
| 發布 | 替換前檢查目的地有否被修改；驗證失敗保留舊檔 |
| 重複執行 | 核對已存在資料，不重複新增或重寫檔案 |

目的地變更檢查不是分散式鎖定。真實整合仍需要符合儲存系統特性的並行存取及恢復設計。

## 可重複執行的檢查

```bash
python -m unittest discover -s tests -v
python scripts/check_docs.py
```

[測試](../tests/test_workflows.py) 涵蓋正常及受阻 CLI 結果、既有資料保留、重跑衝突、異常紀錄、不可讀工作簿、內容被改動、重複標題、不完整傳輸、目的地變更、類似公式的純文字、查詢上限拒絕及墨爾本夏令時間邊界。[CI](../.github/workflows/check.yml) 在 Linux、Windows 及 Python 3.11、3.12 執行檢查。

[舊示範指令](../sample-data/rebuild_workbook_demo.py) 保留為 Avaya 示範的包裝入口。新文件使用 module 入口，讓兩個流程共用同一介面。

## 刻意保留的限制

示範只處理受控的純文字表格，不保留任意公式、圖表、巨集、合併儲存格版面或既有工作簿樣式。示範的 NAS 資料按日期分頁；歷史週末／假期分組政策在案例中說明，這裡並未實作完整日曆規劃器。查詢上限檢查會拒絕一項已知的完整性風險，但不能證明即時 API 資料完整。程式不會進行真實上傳或刪除。通過測試只支持本機參考版本的行為，不能推論每一次歷史執行都符合相同保證。
